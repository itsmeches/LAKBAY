# Technical defense and likely questions

> Evidence snapshot: 12 October 2026; application commit `741f29d`. Documentation-only audit; no FIX-06 implementation, policy activation, data mutation or new dependency.

| Question | Suggested answer | Supporting source |
|---|---|---|
| Why Laravel/Filament? | The work is primarily institutional forms, queues, documents and review. One modular application avoids unnecessary distributed services and shares server-side transition rules. It suits the current team; load/scaling must still be measured. | `composer.lock`; panel providers; `app/Actions` |
| How do screens talk to the backend? | Session-based Laravel web requests and Livewire updates. Protected controllers generate forms and retrieve files. We have no public mobile/REST API in this scope. | `routes/web.php`; `bootstrap/app.php` |
| How is the database organized? | Institutions own activities; versions preserve plans; receipts link exact versions and requirement/evidence snapshots. Reports, monitoring and restricted operational records are linked separately. | migrations; ERDs/data dictionary |
| Why not student accounts? | The selected regional scope is an evidence registry. Consent can be prepared response-only and incident persons are report-specific. No master student or medical-history database is needed. | `PrepareConsentForm`; incident models; architecture scope |
| Who can submit? | An active, email-verified user with the submit permission and verified authorized institutional membership. A preparer alone cannot file. | `Access::owns`; `SubmitActivity::execute` |
| Does CHED approve activities? | Completeness acknowledgment is not conduct authorization. HEI authorization, restrictions and exceptional clearance are separate. External CEB decisions are recorded, not issued by the app. | `IssueAcknowledgment`; `ActivityReadiness`; clearance Actions |
| What if input is wrong? | Validation explains missing fields/evidence; drafts can remain incomplete where designed. Guarded transitions reject invalid/stale state. Transactional failures roll back related writes. | submission/report/case tests and Actions |
| What if a scanner/worker fails? | Files stay quarantined and cannot be downloaded/previewed. Jobs can be retried after the scanner is restored; successful mail deliveries use a ledger. External mail still has a crash/deduplication limit. | `ScanDocument`; notification jobs; browser failure/retry |
| Are all files always integrity checked? | The scanner checks hashes, and some generated-output paths have extra controls. Generic private retrieval does not yet recheck current bytes; FIX-08 is documented. | `DocumentController`; FIX-08 |
| Can an administrator see complaints? | The seeded administrator lacks case-sensitive access. Case records/evidence require the explicit permission and regional access. | `DatabaseSeeder`; `InstitutionRecordPolicy`; browser admin denial |
| How are passwords/MFA protected? | Passwords are hashed; MFA secret/recovery fields are encrypted. Invitations are hashed/expiring and acceptance is one-time. Keys/session/recovery operations need ICT procedures. | `User::casts`; invitation flow |
| Is every download a fresh MFA challenge? | No. The ordinary panel login challenges MFA, while the direct-output middleware checks an active, verified MFA-enrolled user. It does not itself prove a recent challenge. Session/entry-point review remains necessary before claiming universal step-up. | `EnsureMfaEnabled::handle`; panel providers |
| What is the evidence for progress? | Latest retained full results are 497 PHPUnit/2,385 assertions and 38 browser cases, plus static/format/syntax/build checks and local preservation/restore. The report clearly labels environment and coverage limits. | FIX-05 logs and backlog |
| Are all forms exactly CHED-approved? | B–M outputs have local mapping/print tests. Exact Annex K formatting acceptance, N reference publication/order, N/A and scope conventions remain decisions. Typed signatory names are not signatures. | form tests; clarification register; FIX-10/11 |
| Why FIX-06? | Routing and signed decisions exist, but a complete application→endorsement→OSDS staff work→CEB chain is not enforced. We need traceability and explicit unknown historical history. | FIX-06; `RecordClearanceRouting`; `RecordClearanceDecision` |
| Does the ninety-day application replace the three-working-day requirements? | No. They are distinct stages for exceptional clearance and applicable pre-activity evidence. The full interaction/complete-chain workflow remains FIX-06; day-unit clarification is pending. | CMO §27 PDF pp.13–14; §14 PDF pp.7–12 |
| Is CMO 24 active? | No. Issuance is not publication. Activation requires verified publication/reference and publication +15-day effectivity. Candidate evaluation in QA is explicitly local. | §41 PDF p.18; `ConfirmPolicy`; `PolicyRules` |
| What about 48/72-hour reporting? | Under CMO-versioned rules incidents are occurrence +48 hours and ROC is conclusion +72 hours. The formal RCD “upon conduct” anchor is unresolved, not silently changed-at +72. Earlier July records retain their original calculations. | §14 PDF pp.11–12; §§17/25 PDF pp.12–13; `SubmitReport` |
| Is it ready for production? | No. Remaining fixes, policy/publication, PostgreSQL/concurrency/recovery, hosting/mail/security/retention and HEI/CHED pilot sign-off are still gates. | deployment docs; backlog; testing status |
| Can it scale? | Stateless web capacity and more workers are possible architectural options, but shared storage/DB/queues and lock behavior need measured staging tests. No capacity figure is claimed. | monolith architecture; queue/config; unverified load |
| How is maintenance handled? | Shared Actions, named predicates, versioned rules/templates, focused regressions and CI give a maintainable baseline. Change policy prospectively; do not rewrite historical receipts. | classification/policy Actions; CI; activation runbook |
| Can we launch faster by disabling MFA/scanning? | Those protect private and sensitive records. Use an isolated demonstration and resolve setup blockers; the plan does not bypass either control. | AGENTS rules; providers; scanner |

If pressed for a completion date or percentage: explain that release depends on explicit scope decisions and environment validation. Offer a milestone-based sequence in the roadmap rather than a made-up quantitative promise.
